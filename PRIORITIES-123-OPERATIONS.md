# Application reviews, shop pilot and inquiry responses

September 20, 2026. Scope: installers.vicrez.com.

Application review now summarizes services, consent, location and outstanding checks. The note starter fills an empty note; reviewers must replace the outline with actual findings. **Approve and publish** sends an explicit approval decision through the existing transactional review, and a successful approval links to the published listing. Required authority, location and duplicate review remain in place. Existing inquiry opt-outs remain effective.

The authenticated **Shop activation pilot** screen starts with the existing twenty candidates. Candidate status is not participation. Staff may save a partial review, but active participation requires evidence for authority, owner agreement, services/limits, parts policy, hours/response expectation, inquiry consent, recipient verification and an acknowledged, agreed delivery test. The verified email must still match an enabled current routing contact. Changed or disabled recipients no longer count as participating. Pilot decisions do not change listing visibility or contact permissions. Use Contact permissions to stop inquiry delivery. Every pilot decision has a transactional audit and revision conflict check.

Newly routed directory inquiries receive a private shop-response link in their existing email. The link expires 30 days after routing and is signed for one delivery and its recipient, separately from customer receipt tokens. Changed/disabled recipients cannot use it. Opening the link does not record a response. The shop chooses Interested, Need more details (a note is required), or Cannot take this job, then saves explicitly. Responses and their history live with the RFQ SQLite data; retries use an idempotent UUID and edits require the current revision. Responses do not create bookings or send a message to the customer. Customer contact links allow the shop to continue directly.

The inquiry dashboard reports shop responses separately from provider acceptance and staff-recorded quotes/bookings. Response-enabled notifications unanswered after 48 elapsed hours appear for staff review and in the existing daily operations digest. This is an internal follow-up threshold, not a promised response time. Historical notices have no response token and are not replayed or included in this threshold.

Apply `migrations/20260920_pilot.sql` before the website release. Seed only the reviewed candidate IDs using the private deployment script. Deploy `backend/directory_rfq.py` with a source-hash guard and SQLite backup; its additive tables are created at startup. Publish the response page before adding its link to the live email template. Keep the existing flow recipient and status configuration. No dependency or credential rotation is required.

Private response pages are noindex, use no-referrer and no-store responses, and exclude analytics and attribution scripts. Tokens stay in the URL fragment and POST body; do not add them to logs or staff/public API output. Revoke a compromised link by setting `directory_response_access.revoked=1` for the exact delivery after preserving its audit evidence. Never mass-replay delivered inquiries as a repair.

Recovery: keep the additive PostgreSQL and SQLite tables and all accepted requests. Restore code or the backed-up email template only after checking for subsequent changes. Prefer a corrective release over restoring an older database. No real application approval, owner confirmation, inquiry, response, quote or booking is fabricated by deployment.
